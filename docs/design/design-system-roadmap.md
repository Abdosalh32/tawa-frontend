# خارطة طريق نظام التصميم (Design System Roadmap) — منصة توا

> ترتيب تنفيذ عملي لنظام التصميم — **دون كود في هذه المرحلة**. كل مرحلة بمعايير قبول صريحة تُفحص قبل الانتقال.
> المراجع: `design-system-foundations.md` (الأسس)، `component-inventory.md` (الجرد)، `page-patterns.md` (الأنماط)، `design-decision-log.md` (المعلّقات D1–D10).

---

## المرحلة 1 — الأساس (Foundation)

**النطاق:** ترجمة أدوار الأسس إلى Tokens فعلية: الألوان الدلالية الثلاث تجارب (`accent.merchant/admin/store`)، سلّما الطباعة والمسافات، الأسطح والحدود والزوايا، نقاط التحول، قواعد RTL والأرقام (§8).

**معايير القبول:**
- [ ] كل دور مسمى في الأسس له قيمة واحدة معتمدة — لا قيم خام خارج الأدوار
- [ ] فحص تباين موثّق لكل تركيبة نص/خلفية معتمدة (بما فيها الشارات) بنتيجة ≥AA
- [ ] `accent.store` مبني كمتغير قابل للاستبدال منذ اليوم الأول (لا أزرق مثبت في الستورفرونت)
- [ ] صفحة اختبار RTL تعرض: جملة عربية بكود لاتيني معزول، مبلغاً، هاتفاً، تاريخاً — كلها سليمة الاتجاه

## المرحلة 2 — البدائيات الجوهرية (Core Primitives)

**النطاق:** زر، زر أيقوني، غلاف الحقل، إدخال نصي/رقمي/هاتف/كلمة مرور، منطقة نص، Select، خانة اختيار، راديو، مفتاح، شارة حالة، Toast، حوار (+ نمط التأكيد المدمر)، Tooltip، Skeleton.

**معايير القبول:**
- [ ] كل بدائية بكامل حالاتها القياسية + الإضافية المذكورة في الجرد
- [ ] التشغيل الكامل بلوحة المفاتيح موثّق ومجرَّب لكل بدائية (تركيز، Esc، أسهم حيث تلزم)
- [ ] حوار التأكيد المدمر يطبق النمط الملزم (أثر محدد + سبب إلزامي + تركيز على الإلغاء)
- [ ] لا بدائية تستخدم لوناً خاماً — أدوار فقط

## المرحلة 3 — المكونات المشتركة (Shared Components)

**النطاق:** بحث وفلاتر (+Chips)، تبويبات، ترقيم، Stepper، بطاقات (عامة/مؤشر)، جدول البيانات + بطاقة الصف للهاتف + التحرير الموضعي، Drawer، Popover/⋮، Banner، Alert، الحالات الست (فارغة/خطأ/غير مصرّح…)، Avatar وقائمة المستخدم، رفع صورة، إدخال OTP، إدخال تاريخ، Combobox، قواميس الحالات (طلب/مخزون/اعتماد).

**معايير القبول:**
- [ ] الجدول يتحول بطاقة صف تلقائياً تحت `bp.desktop` دون فقد المعلومة الحرجة
- [ ] قاموس شارات موحد واحد تستهلكه كل الشاشات (لا تعريف حالة محلياً)
- [ ] كل مكون قائمة يشحن بحالاته: فارغة-حقيقية، فارغة-بفلتر، تحميل Skeleton، خطأ بإعادة محاولة
- [ ] OTP يقبل اللصق دفعة واحدة ويعمل كحقل واحد للقارئات

## المرحلة 4 — أنماط لوحة التاجر

**النطاق:** هيكل اللوحة (قائمة جانبية + شريط علوي + شريط حالة المتجر)، ثم P4 (نظرة عامة)، P5 (القوائم: منتجات، مخزون، طلبات)، P6 (نموذج المنتج بالمتغيرات)، P9 (الإعدادات + Checklist النشر)، معالج الإعداد الأولي، وشاشات المصادقة (F1).

**لماذا التاجر أولاً:** أكبر مساحة شاشات، ويختبر النظام بأقسى حالاته (جداول، نماذج مركبة، حالات متجر) قبل تفريعه.

**معايير القبول:**
- [ ] رحلة كاملة قابلة للنقر: تسجيل ← OTP ← معالج ← إضافة منتج بمتغيرات ← طلب تجريبي ينقل حالاته ← Checklist النشر
- [ ] أرقام المخزون الثلاثة (كلي/محجوز/متاح) لا تلتبس في أي شاشة، والمحجوز مُفسَّر بتلميح (1.4.11)
- [ ] شريط حالة المتجر يظهر صحيحاً للحالات: غير معتمد، غير منشور، صيانة، معلّق
- [ ] كل شاشة بإجراء أساسي واحد لا أكثر
- [ ] ملاحة الموظف المقلّصة تُخفي (لا تعطّل) غير المصرّح به — بمنطق مبسط حتى حسم D10

## المرحلة 5 — أنماط الستورفرونت

**النطاق:** P1 (التصفح)، P2 (صفحة المنتج)، P3 (السلة والـ Checkout كاش فقط)، شاشة التتبع (F6)، صفحة الصيانة، الفوتر والسياسات — كلها فوق `accent.store`.

**معايير القبول:**
- [ ] رحلة شراء كاملة من الهاتف: تصفح ← فلترة ← منتج ← سلة ← شحن ← كاش ← رقم تتبع ← تتبع ناجح
- [ ] تبديل قيمة `accent.store` تجريبياً (3 ألوان متباينة الفتوح) لا يكسر تبايناً ولا مكوناً
- [ ] كتلة القرار كاملة فوق خط الطي في هاتف 360px عرضاً
- [ ] كل أهداف اللمس ≥44 وتجربة الإبهام سليمة للأزرار الملتصقة
- [ ] رسائل المخزون تطابق المتطلبات: «المتاح 3 فقط» عند التجاوز (2.2.2)، نفاد معطَّل الإضافة

## المرحلة 6 — أنماط لوحة المدير

**النطاق:** هيكل اللوحة بـ `accent.admin`، P7 (طابور الاعتماد والمراجعة — بعارض وثائق عام بانتظار D3)، P8 (المتاجر، فحص المنتجات الشبكي، سجل التدقيق)، حوارات القرارات المسبَّبة.

**معايير القبول:**
- [ ] اللون الإداري يميز اللوحة فوراً دون أي تسمية — اختبار لقطة شاشة جنباً إلى جنب مع لوحة التاجر
- [ ] الرفض والحظر لا يكتملان دون سبب، والصياغة تعرض الأثر بالأسماء الفعلية
- [ ] سجل التدقيق بلا أي عنصر تحرير، والعمليات الحرجة موسومة أثقل
- [ ] الاعتماد والرفض متكافئا الوزن البصري في شاشة المراجعة

## المرحلة 7 — تحقق الإتاحة وRTL الشامل

**النطاق:** مراجعة عرضية بعد اكتمال التجارب الثلاث (لا تلغي فحوص المراحل — تجمعها).

**معايير القبول:**
- [ ] تنقل بلوحة المفاتيح فقط عبر الرحلات الثلاث الكاملة دون أي فخ تركيز
- [ ] فحص قارئ شاشة للمسارات الحرجة: OTP، إضافة للسلة، تأكيد الطلب، قرار اعتماد
- [ ] تدقيق تباين آلي + يدوي للشارات والحالات فوق كل الخلفيات المعتمدة
- [ ] فحص RTL شامل: لا أيقونة اتجاهية غير منعكسة، لا كود/هاتف مكسور الاتجاه، والتاب يتبع الترتيب البصري
- [ ] `prefers-reduced-motion` يعطّل النبض والانتقالات غير الضرورية
- [ ] تجربة نصوص عربية طويلة فعلية (أسماء منتجات ومتاجر حقيقية الطول) بلا قصّ مخلّ

## المرحلة 8 — المسارات المؤجلة (بعد حسم قرارات المنتج)

**النطاق والاعتماديات:**

| المسار | ينتظر |
|---|---|
| خطوة الشحن النهائية + إدارة الشحن | **D1** |
| شاشة معاملات البطاقة + حالات فشل الدفع | **D2** |
| رفع الوثائق في التسجيل + عارض المراجعة النهائي | **D3** |
| قسم الاشتراك عند التاجر + بطاقات الباقات الإدارية | **D4** |
| مبدّل المتاجر (إن نُقض A1) | **D5** |
| منتقي ألوان التاجر النهائي وحدوده | **D6** |
| مركز الإشعارات (الجرس) | **D7** |
| سلوك انتهاء الحجز في السلة | **D8** |
| الخصومات (لوحة + سلة) | **D9** |
| مصفوفة الصلاحيات النهائية | **D10** |

**معايير القبول:**
- [ ] لا مسار مؤجل بُني على تخمين — كل بند يبدأ بقرار موثّق في `design-decision-log.md` بتاريخ وحسم
- [ ] المكونات المبنية سابقاً تستوعب الإضافة دون كسر (اختبار: إضافة سطر الشحن للملخص لا يعيد تصميمه)

---

## قواعد عابرة للمراحل

1. **لا يُبنى مكون خارج الجرد** — الإضافة تمر بتحديث `component-inventory.md` أولاً.
2. **المعلّقات لا تُحل ارتجالاً** — أي بند `Pending product decision` يُبنى له أبسط Placeholder موثّق أو يُترك.
3. **كل مرحلة تنتهي بمراجعة ضد وثائق UX** — الشاشة التي تخالف مساراً في `user-flows.md` ترجع لا تتقدم.
4. **الترتيب داخل المرحلة يقوده الاعتماد لا السهولة** — لا مكون قبل بدائياته.
