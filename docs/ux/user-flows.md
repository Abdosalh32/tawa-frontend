# مسارات المستخدم (User Flows) — منصة توا

> **مصدر الحقيقة:** `docs/requirements/توا-المتطلبات.pdf`. البنود الموسومة **[افتراض]** أو **[سؤال مفتوح]** ليست في المتطلبات.
> ترقيم بنود مدير المنصة بصيغة **م.1.3.x** (انظر ملاحظة الترقيم في `product-model.md`).

**فهرس المسارات**

| # | المسار | الدور |
|---|---|---|
| F1 | التسجيل والتفعيل وتسجيل الدخول | تاجر |
| F2 | تجهيز المتجر ونشره (وإلغاء النشر) | تاجر |
| F3 | إدارة المنتجات والمتغيرات والمخزون | تاجر |
| F4 | إدارة الطلبات | تاجر |
| F5 | التصفح والسلة وإتمام الشراء والدفع | زبون |

| F8 | الرقابة: المتاجر والمنتجات المخالفة | مدير |
| F9 | الباقات والاشتراكات وسجل التدقيق | مدير |
| F10 | دعوة الموظفين وإدارة الصلاحيات | تاجر + موظف |

## F1 — تسجيل التاجر وتفعيله ودخوله (1.1.1 – 1.1.5)

**المحفّز:** تاجر جديد يريد فتح متجر على المنصة.

**الخطوات الرئيسية**
1. يفتح صفحة التسجيل ويُدخل: الاسم، البريد، رقم الهاتف، كلمة المرور (1.1.1).
2. يستلم رمز OTP برسالة نصية ويدخله في شاشة التفعيل (1.1.2).
3. عند النجاح يتفعّل الحساب وينتقل لمعالج إعداد المتجر (F2) — الربط الفوري من (1.2.1: «فور التسجيل»).
4. لاحقاً: تسجيل الدخول ببيانات الاعتماد (1.1.3).
5. عند النسيان: طلب استعادة → رابط آمن مؤقت عبر البريد أو الهاتف → شاشة تعيين كلمة مرور جديدة وتأكيدها (1.1.4 – 1.1.5).

**نتيجة النجاح:** حساب مفعّل بهاتف موثّق، وجلسة دخول إلى لوحة التحكم.

**الحالات الحدّية / الفشل**
- بيانات مستخدمة مسبقاً (هاتف/بريد) → رسالة خطأ على الحقل نفسه. **[افتراض]** المتطلبات لا تنص على قاعدة التفرد لكنها لازمة لـ«تأكيد ملكية الرقم».
- رمز OTP لم يصل → إعادة إرسال. **[افتراض من وثيقة التحليل]** بعد عدّاد 60 ثانية.
- رمز خاطئ أو منتهي → رسالة خطأ ومحاولة جديدة. **[سؤال مفتوح]** حد المحاولات ومدة صلاحية الرمز.
- رابط الاستعادة منتهي الصلاحية → طلب رابط جديد.
- **[سؤال مفتوح]** هل يسجّل الدخول بالبريد أم الهاتف أم كليهما؟ (1.1.3 تقول «بيانات الاعتماد» فقط.)

**الشاشات المتوقعة لاحقاً:** تسجيل، إدخال OTP، دخول، طلب استعادة، تعيين كلمة مرور جديدة.

## F2 — تجهيز المتجر ونشره (1.2.x، 1.3.x)

**المحفّز:** حساب تاجر مفعّل حديثاً، أو تاجر يجهّز متجره للإطلاق.

**الخطوات الرئيسية**
1. **الإعداد الأولي (1.2.1):** معالج فور التسجيل: اسم المتجر → اللغة → حجز النطاق الفرعي مع تحقق فوري من التوفر.
2. **المظهر (1.3.1 – 1.3.4):** استعراض مكتبة القوالب المعتمدة (RTL ومتجاوبة) → تثبيت قالب بنقرة → تخصيص الألوان (رئيسي/ثانوي/خلفيات هيدر وفوتر) → ترتيب أقسام الصفحة الرئيسية وإظهارها/إخفاؤها.
3. **المعاينة (1.3.5):** رؤية النتيجة في بيئة معاينة معزولة لا تؤثر على المتجر المنشور.
4. **إضافة المنتجات** (F3) والسياسات الإلزامية.
5. **النشر (1.2.4):** زر النشر يتاح بعد استيفاء المتطلبات (منتجات + سياسات إلزامية + اعتماد الإدارة م.1.3.2).
6. **إلغاء النشر عند الحاجة (1.2.5):** إيقاف مؤقت لاستقبال الطلبات → صفحة صيانة للزوار → الطلبات السابقة تبقى قابلة للإدارة.

**نتيجة النجاح:** متجر منشور يستقبل الزوار والطلبات على نطاقه الفرعي.

**الحالات الحدّية / الفشل**
- النطاق محجوز → رسالة فورية. **[توصية من وثيقة التحليل]** عرض اقتراحات بديلة.
- محاولة نشر قبل استيفاء المتطلبات → زر معطّل مع Checklist يوضح الناقص. **[توصية]**
- المتجر غير معتمد بعد → حالة «بانتظار اعتماد الإدارة» ظاهرة في اللوحة.
- تغييرات مظهر غير منشورة → تبقى في المعاينة حتى النشر. **[سؤال مفتوح]** هل نشر تغييرات المظهر منفصل عن نشر المتجر نفسه؟
- **[سؤال مفتوح]** هل يمكن تغيير النطاق الفرعي بعد الحجز؟ (1.2.3 تذكر تعديل الاسم واللغة والشعار، لا النطاق.)

**الشاشات المتوقعة:** معالج الإعداد (3 خطوات + نجاح)، مكتبة القوالب، تخصيص الألوان، ترتيب الأقسام، معاينة، إعدادات المتجر (النشر/الحالة)، صفحة الصيانة العامة.

## F3 — المنتجات والمتغيرات والمخزون (1.4.x)

**المحفّز:** التاجر يبني كتالوجه أو يديره يومياً.

**الخطوات الرئيسية**
1. قائمة المنتجات مصنّفة بحسب الفئة (1.4.1) → «منتج جديد».
2. إدخال البيانات: الاسم، الوصف، الفئة، الصور، السعر (1.4.3).
3. عند الحاجة، تفعيل المتغيرات: تعريف محاور متقاطعة (مثل مقاس S/M × لون أحمر/أزرق) فتتولّد التركيبات (1.4.6).
4. لكل متغير: سعر ومخزون وصورة مستقلة (1.4.7)، وحذف التركيبات غير المتاحة (1.4.8).
5. متابعة المخزون: الصافي المتاح = الكمية − المحجوز مؤقتاً (1.4.9، 1.4.11)، وتعديل يدوي للكميات بعد الجرد (1.4.10).
6. استلام تنبيه فوري عند انخفاض كمية منتج (1.4.12).
7. عند انتهاء دورة حياة المنتج: أرشفة تخفيه مع حفظ سجلاته (1.4.5).

**نتيجة النجاح:** كتالوج دقيق المخزون يظهر منه المنشور فقط في واجهة الزبون.

**الحالات الحدّية / الفشل**
- حذف متغير له طلبات سابقة → **[سؤال مفتوح]** المتطلبات تجيز «إزالة الخيار الفرعي غير المتاح» (1.4.8) وتمنع كسر الطلبات القديمة (1.4.5) — يلزم تحديد السلوك (أرشفة المتغير بدل حذفه؟).
- أرشفة منتج موجود في سلات نشطة أو محجوز → **[سؤال مفتوح]** غير محدد.
- تعديل يدوي أثناء وجود حجوزات نشطة → المتاح لا يجب أن يقل عن المحجوز. **[افتراض]**
- **[سؤال مفتوح]** عتبة «انخفاض المخزون» (1.4.12): ثابتة أم يحددها التاجر لكل منتج؟ وقناة التنبيه؟

**الشاشات المتوقعة:** قائمة المنتجات (مع بحث/تصفية وحالات فارغة)، نموذج إضافة/تعديل منتج مع محرر المتغيرات وجدول التركيبات، شاشة المخزون مع تعديل سريع ومؤشر المحجوز، نافذة تعديل يدوي.

## F4 — إدارة الطلبات لدى التاجر (1.5.2 – 1.5.5)

**المحفّز:** وصول طلب جديد من زبون.

**الخطوات الرئيسية**
1. عرض قائمة الطلبات الواردة مع تصفية بحسب حالات منفصلة: الطلب / الدفع / التوصيل (1.5.2).
2. فتح تفاصيل الطلب: عناصر الشراء، بيانات العنوان، رسوم الشحن (1.5.3).
3. نقل الحالة تدريجياً: مؤكد → قيد التجهيز → جاهز للتسليم → مسلّم (1.5.4).
4. عند التعذر: إلغاء الطلب فترجع الكميات المخصومة للمخزن آلياً (1.5.5).

**نتيجة النجاح:** طلب مسلّم بحالة نهائية صحيحة، أو ملغى مع مخزون مستعاد.

**الحالات الحدّية / الفشل**
- **[سؤال مفتوح]** من أي الحالات يجوز الإلغاء؟ وهل يُسمح بالرجوع خطوة للخلف؟
- **[سؤال مفتوح]** إلغاء طلب مدفوع بالبطاقة: هل يوجد استرجاع مالي؟ غير مذكور.
- **[سؤال مفتوح]** هل يُشعر الزبون بتغيّر الحالة (SMS مثلاً)؟ غير مذكور — الزبون يرى الحالة عبر التتبع (F6).
- طلب يحوي منتجاً أُرشف لاحقاً → يظل قابلاً للإدارة (مضمون بقاعدة 1.4.5).

**الشاشات المتوقعة:** قائمة الطلبات (تبويبات حالات + فلاتر دفع/توصيل)، تفاصيل الطلب مع شريط تقدم الحالة، نافذة تأكيد الإلغاء.

---

## F5 — تسوق الزبون: تصفح → سلة → دفع (2.1.x، 2.2.1 – 2.2.7)

**المحفّز:** زبون يفتح نطاق متجر منشور.

**الخطوات الرئيسية**
1. تصفح المنتجات المنشورة المتاحة للشراء (2.1.1).
2. بحث فوري بالكلمات في العناوين والأصناف والرموز (2.1.2)، وتصفية بالفئة الرئيسية/الفرعية (2.1.3)، وفلترة بالسعر (أدنى/أقصى) واللون والمقاس (2.1.4).
3. صفحة المنتج: صور، أوصاف, سياسات، اختيار المتغير والتحقق من توفره (2.1.5).
4. إضافة المنتج/المتغير بكمية محددة للسلة (2.2.1)؛ عند بدء الشراء تُحجز الكمية 15 دقيقة (1.4.11).
5. في السلة: تعديل الكميات مع تحقق فوري من المخزون (2.2.2)، حذف عنصر بنقرة (2.2.3)، ورؤية الإجمالي (2.2.4).
6. إدخال بيانات الشحن: العنوان، رقم الهاتف، مكان الاستلام (2.2.5).
7. اختيار الدفع: كاش عند الاستلام، أو بطاقة مصرفية عبر شاشة معاملات (2.2.7).
8. تأكيد الطلب → إنشاء رقم تتبع فريد يمنع التكرار (2.2.6) → شاشة نجاح تبرز الرقم.

**نتيجة النجاح:** طلب مسجّل لدى التاجر، والزبون يملك رقم تتبع + هاتفه للمتابعة.

**الحالات الحدّية / الفشل**
- الكمية المطلوبة تتجاوز المتاح → رسالة بالمتاح الفعلي وتقييد الكمية (2.2.2).
- نفاد المنتج أثناء التصفح → «غير متوفر» وتعطيل الإضافة. **[توصية من وثيقة التحليل]**
- انتهاء مهلة الحجز (15 دقيقة) قبل التأكيد → **[سؤال مفتوح]** السلوك غير محدد (تحرير الحجز وإعادة التحقق عند التأكيد؟).
- فشل معاملة البطاقة → **[سؤال مفتوح]** غير محدد (إعادة محاولة؟ تحويل لكاش؟ مصير الحجز؟).
- متجر أُلغي نشره أثناء الجلسة → صفحة الصيانة (1.2.5).
- إعادة إرسال التأكيد مرتين → يمنعه تفرّد رقم التتبع (2.2.6).
- **[سؤال مفتوح]** تطبيق الخصم (1.5.1) في السلة: تلقائي عند بلوغ الحد الأدنى أم بكود؟ المتطلبات لا تذكر كوبونات.

**الشاشات المتوقعة:** واجهة المتجر الرئيسية، قائمة/شبكة منتجات مع فلاتر، نتائج بحث، صفحة منتج، السلة، بيانات الشحن والدفع، شاشة معاملات البطاقة، تأكيد النجاح، صفحة صيانة، صفحات السياسات.

## F6 — تتبع الطلب دون حساب (2.2.8)

**المحفّز:** زبون يريد معرفة حالة شحنته.

**الخطوات:** فتح صفحة «تتبع طلبك» → إدخال رقم الطلب + رقم الهاتف → عرض مسار الحالة وحالتها الحالية.

**نتيجة النجاح:** رؤية حالة الشحنة عبر المراحل (مؤكد → قيد التجهيز → جاهز للتسليم → مسلّم).

**الحالات الحدّية:** لا تطابق بين الرقمين → «لا يوجد طلب مطابق». طلب ملغى → عرض حالة الإلغاء. **[افتراض]**

**الشاشات المتوقعة:** نموذج الاستعلام، نتيجة التتبع (خط زمني)، حالة الخطأ.

---

## F7 — اعتماد التجار (م.1.3.1 – م.1.3.3)

**المحفّز:** طلبات انضمام جديدة في قائمة الانتظار.

**الخطوات الرئيسية**
1. عرض قائمة طلبات الانضمام والوثائق المرفوعة (م.1.3.1).
2. فتح طلب: بيانات التاجر + الوثائق.
3. **قرار أ — اعتماد:** تفعيل الحساب رسمياً؛ يستطيع التاجر النشر (م.1.3.2).
4. **قرار ب — رفض:** إدخال سبب إلزامي؛ يظهر للتاجر ليصحح ويعيد التقديم (م.1.3.3).

**نتيجة النجاح:** كل طلب في القائمة يؤول إلى معتمد أو مرفوض مسبَّب.

**الحالات الحدّية / الفشل**
- **[سؤال مفتوح]** ما الوثائق المطلوبة تحديداً؟ وهل رفع الوثائق جزء من تسجيل التاجر (1.1.1 لا تذكره)؟ فجوة يجب حسمها لأنها تغيّر مسار F1.
- **[سؤال مفتوح]** هل يوجد قرار وسيط «طلب استكمال وثائق» دون رفض كامل؟ (وثيقة التحليل تقترحه توصيةً.)
- إعادة تقديم بعد الرفض → يظهر الطلب مجدداً في القائمة مع تاريخه. **[افتراض]**

**الشاشات المتوقعة:** قائمة الطلبات بتبويبات، شاشة مراجعة تفصيلية مع عارض وثائق، نوافذ تأكيد الاعتماد/الرفض.

---

## F8 — الرقابة: المتاجر والمنتجات (م.1.3.4 – م.1.3.9)

**المحفّز:** فحص دوري، أو رصد مخالفة.

**الخطوات الرئيسية**
1. تصفح كل المتاجر بحالاتها ونطاقاتها (م.1.3.6) ومعاينة متجر معيّن للتحقق من جودة ومشروعية المحتوى (م.1.3.7).
2. فحص المنتجات عبر كل المتاجر لضمان خلوها من المحظور (م.1.3.8).
3. عند مخالفة منتج: حظره وإزالته فوراً + إشعار التاجر بدليل الإزالة (م.1.3.9).
4. عند مخالفة تاجر: حظر/تعليق حسابه وإغلاق متجره (م.1.3.4)، ثم فك الحظر بعد معالجة الأسباب (م.1.3.5).
5. كل هذه العمليات الحساسة تُسجّل في سجل التدقيق (م.1.3.13). **[افتراض]** كون الحظر والاعتماد «عمليات حساسة».

**نتيجة النجاح:** منصة خالية من المحتوى المخالف مع أثر تدقيقي كامل وقابلية تراجع (فك الحظر).

**الحالات الحدّية / الفشل**
- حظر تاجر له طلبات جارية → **[سؤال مفتوح]** مصير الطلبات قيد التنفيذ غير محدد.
- ماذا يرى زوار متجر محظور؟ → **[سؤال مفتوح]** (صفحة صيانة؟ رسالة مختلفة؟)
- **[سؤال مفتوح]** هل يوقف تعليقُ التاجر اشتراكَه المدفوع أو يمدده؟

**الشاشات المتوقعة:** قائمة المتاجر مع فلاتر حالة، معاينة متجر، شبكة فحص المنتجات، نافذة حظر منتج (سبب + دليل)، نافذة تعليق/فك تعليق تاجر.

---

## F9 — الباقات والاشتراكات وسجل التدقيق (م.1.3.10 – م.1.3.13)

**المحفّز:** إدارة العرض التجاري للمنصة ومتابعة الإيراد.

**الخطوات الرئيسية**
1. إنشاء باقة جديدة: الخدمات وحدودها وسعرها (م.1.3.10).
2. تعديل حدود وأسعار باقة قائمة (م.1.3.11). **[سؤال مفتوح]** أثر التعديل على المشتركين الحاليين.
3. أرشفة باقة: منع التقديم الجديد مع استمرار المشتركين (م.1.3.11ب).
4. تجديد اشتراك تاجر يدوياً بعد استلام السداد (م.1.3.12) — يدل على سداد خارج المنصة (كاش/تحويل). **[افتراض]**
5. مراجعة سجل التدقيق بالقراءة فقط (م.1.3.13).

**نتيجة النجاح:** باقات محدّثة واشتراكات سارية وسجل كامل للعمليات الحساسة.

**الحالات الحدّية / الفشل**
- **[سؤال مفتوح]** انتهاء اشتراك التاجر دون تجديد: تعليق تلقائي؟ فترة سماح؟ غير محدد.
- **[سؤال مفتوح]** كيف يختار التاجر باقته ابتداءً؟ لا يوجد بند لعرض الباقات في لوحة التاجر — فجوة صريحة.
- تخفيض حدود باقة تحت استخدام تاجر فعلي (مثلاً منتجاته أكثر من الحد الجديد) → غير محدد.

**الشاشات المتوقعة:** بطاقات الباقات مع الأرشفة، نموذج إنشاء/تعديل باقة، جدول/نافذة تجديد يدوي، شاشة سجل التدقيق مع فلاتر.

---

## F10 — الفريق والصلاحيات (1.5.7 – 1.5.9)

**المحفّز:** التاجر يحتاج مساعدة في تشغيل المتجر.

**الخطوات الرئيسية**
1. التاجر يرسل دعوة بالبريد لموظف جديد لمنحه وصولاً للوحة التحكم (1.5.7).
2. الموظف يقبل الدعوة وينشئ بيانات دخوله. **[افتراض]** آلية القبول وإنشاء كلمة المرور غير مفصّلة في المتطلبات.
3. التاجر يحدد الأدوار والوظائف المسموح للموظف الوصول إليها (1.5.8).
4. عند الحاجة: تعطيل الحساب وسحب الصلاحيات فوراً (1.5.9).

**نتيجة النجاح:** موظف نشط يرى من اللوحة ما سُمح له به فقط، وقابلية إيقاف فورية.

**الحالات الحدّية / الفشل**
- دعوة لم تُقبل → حالة «بانتظار القبول» مع إعادة إرسال. **[توصية]**
- موظف معطّل يحاول الدخول → رفض الجلسة فوراً (1.5.9: «فوراً»).
- موظف يفتح شاشة بلا صلاحية → حالة «غير مصرّح» واضحة. **[توصية]**
- **[سؤال مفتوح]** هل توجد أدوار جاهزة (مدير/موظف) أم صلاحيات حرة فقط؟ (1.5.8 تذكر «الأدوار والوظائف» معاً دون تفصيل.)
- **[سؤال مفتوح]** حد عدد الموظفين مرتبط بالباقة؟

**الشاشات المتوقعة:** قائمة الفريق بحالاتهم، نموذج دعوة مع مصفوفة صلاحيات، نافذة تعطيل، شاشة قبول الدعوة (للموظف)، حالة «غير مصرّح».
